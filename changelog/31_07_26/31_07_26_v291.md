# Changelog
## [v2.9.1]

# Patch: Hardcoded Email Detection in JS

## Problem

`jsintel.Learn` had no regex for email addresses. Emails embedded in JS
logic (e.g. `if (email === "admin@corp.com")`, config objects, minified
bundles) were invisible to recon. Only `mailto:` links parsed in
`extractHTML` were captured, via `e.k.AddEmail()`.

## Change

### `internal/recon/jsintel/jsintel.go`

- Added `reEmail` to the regex var block:
  ```go
  reEmail = regexp.MustCompile(`\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}\b`)
  ```
- `Learn` signature changed to accept the knowledge graph:
  ```go
  func Learn(k *knowledge.Knowledge, ent *knowledge.Entity, sourceURL string, body []byte) []JSEndpoint
  ```
- New detection block (Secrets/keys section, after the Firebase config check):
  - Every match is recorded per-entity via `appendLeak(ent, "email", sourceURL, "", email)` — dedupes through the existing `ent.Content.SeenJSLeaks` map, same pattern as `jwt`/`aws_key`.
  - Every match is also pushed to the global list via `k.AddEmail(email)`, guarded by a `k != nil` nil check — this puts JS-sourced emails in the same global list as HTML `mailto:` emails instead of a separate silo.
  - **No cap** on the loop (unlike `jwt`/`aws_key`/`keyword`, capped at 5). Safe because `appendLeak`'s dedupe key (`kind|key|value`) already collapses repeats per entity; the only effect of no cap is more calls into `k.AddEmail`, whose own dedup behavior is separate and unverified as of this patch.

### Call sites updated (signature change)

- `internal/recon/http/html.go` — inline `<script>` branch:
  ```go
  jsintel.Learn(e.k, ent, ent.URL+"#inline", []byte(code.String()))
  ```
- `internal/recon/http/learn.go` — external JS fetch branch:
  ```go
  jsEndpoints := jsintel.Learn(e.k, ent, url, body)
  ```

## Result

Verified against a live scan (`hosperty.vercel.app`): 10 unique emails
surfaced in both the global `CONTACT INFO` report section and the
per-asset `[email]` JS leak listing, with no duplicates between the two.

## Known follow-ups (not part of this patch, not yet actioned)

- `reJWT` produces false positives on dotted minified identifiers
  (e.g. `persistence.referenceDelegate.updateLimboDocument` matches the
  three-segment shape of a JWT). Needs tightening, pending sign-off.
- No dedup verification done on `k.AddEmail` itself — if it doesn't
  dedupe globally, a bundle with a repeated email could push duplicate
  entries into the global list even though `JSLeaks` stays clean per entity.
